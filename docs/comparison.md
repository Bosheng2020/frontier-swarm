# Multi-Agent Framework Comparison: eve, LangGraph, AutoGen, CrewAI, OpenAI Agents SDK, and Google ADK

> **Scope:** This is a capability map based on official documentation checked on 2026-10-22, not a benchmark, endorsement, or maturity ranking. Similar feature names can hide different execution, context, persistence, and security semantics. Frontier Swarm has no published head-to-head results, so this table makes no quality, latency, cost, safety, or state-of-the-art claim.

| Project | Primary abstraction | Multi-agent coordination | State and execution | Evaluation and operations | Important boundary |
| --- | --- | --- | --- | --- | --- |
| [eve Council of Agents](https://eve.dev/templates/eve-llm-council-template) | An official TypeScript/Next.js reference template on eve, rather than a separate general-purpose framework. | A root agent sends the same prompt to four declared subagents in parallel, then a judge returns a structured answer and per-model agreement scores. | Each member runs in its own durable session and its child stream can be followed independently. General eve [subagents](https://eve.dev/docs/subagents) run as asynchronous tasks with isolated specialist capabilities. | eve [evals](https://eve.dev/docs/evals/overview) exercise real agent sessions and support deterministic fixtures, assertions, judges, and optional reporters. | A fixed council-and-judge example does not establish better accuracy or state-of-the-art performance. The live template can evolve; projects pinned to an eve version should use that version's bundled docs. |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | A low-level graph runtime for long-running, stateful agents; nodes and edges can mix deterministic code with model-driven steps. Python and JavaScript documentation are available. | Custom graphs can express routing, fan-out, joins, loops, and subgraphs. LangChain's official [multi-agent guide](https://docs.langchain.com/oss/python/langchain/multi-agent) describes subagents, handoffs, skills, routers, and custom LangGraph workflows. | [Checkpointers and stores](https://docs.langchain.com/oss/python/langgraph/persistence) provide thread-scoped checkpoints and cross-thread data; durable execution, streaming, and interrupts support recovery and human review. | LangSmith is the separately named companion for tracing, evaluation, and managed deployment. | LangGraph intentionally does not prescribe prompts or a team topology. The developer owns graph design and context engineering; the docs note that many tasks still fit one agent. |
| [Microsoft AutoGen AgentChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/) | A Python high-level multi-agent API built on the event-driven AutoGen Core. | Official [team presets](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html) include round-robin, model-selected group chat, Magentic-One, and handoff-based Swarm. [GraphFlow](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/graph-flow.html) adds sequential, parallel, conditional, and looping graph execution. | Teams retain conversational state between runs; agents and teams expose explicit [save/load state](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/state.html) APIs for application-managed persistence. | The official surface includes termination, cancellation, logging, and tracing/observability guides. | GraphFlow is explicitly experimental. Several team presets broadcast a shared context, which differs materially from isolated specialist sessions; the docs recommend starting with one agent when it is sufficient. |
| [CrewAI](https://docs.crewai.com/en/concepts/crews) | A Python framework with role/task-based Crews for collaboration and event-driven Flows for controlled automation. | Crew [processes](https://docs.crewai.com/en/concepts/processes) are sequential or hierarchical; [tasks](https://docs.crewai.com/en/concepts/tasks) can execute asynchronously and feed later tasks. [Flows](https://docs.crewai.com/en/concepts/flows) add state, routing, branching, loops, and composition of crews. | Flow `@persist` can recover state across restarts, using SQLite by default or a custom backend; current Crew configuration also exposes checkpointing. | Crew tracing, testing, event listeners, and third-party observability integrations are documented. | An autonomous Crew and a deterministic Flow are different execution models. Comparisons should name which one is used; “CrewAI” alone does not imply a particular topology or durability policy. |
| [OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk) | A code-first TypeScript and Python SDK whose runner owns the agent loop while the application owns deployment, tools, storage, and approval decisions. | Official [orchestration guidance](https://developers.openai.com/api/docs/guides/agents/orchestration) distinguishes handoffs, where a specialist takes over the reply, from agents as tools, where the manager retains control and synthesizes. | Applications choose SDK sessions, Responses conversation state, or their own storage and runtime integration; sandbox and resumable-state surfaces are documented separately. | Guardrails, human review, tracing, MCP, and integrations are first-class documented surfaces. | It is not a preconfigured council or fixed DAG. The two orchestration patterns have different ownership semantics, and the docs advise adding specialists only when isolation or clearer contracts justify the extra prompts, traces, and approvals. |
| [Google Agent Development Kit](https://adk.dev/workflows/collaboration/) | A multi-language agent/workflow SDK with coordinator-subagent collaboration, template workflows, and newer graph workflows. Feature availability varies by language and version. | Collaboration modes are `chat`, `task`, and `single_turn`; only `single_turn` supports parallel calls. Deterministic [ParallelAgent](https://adk.dev/agents/workflow-agents/parallel-agents/) and SequentialAgent templates are also documented, while ADK 2.0 adds [graph workflows](https://adk.dev/graphs/). | [Session, State, and Memory](https://adk.dev/sessions/) separate current-thread context from searchable cross-session memory; services select in-memory, database, or cloud persistence. Parallel branches are isolated by default and require explicit result/state coordination. | The official documentation includes evaluation, logging, metrics, traces, deployment, and A2A interoperability. | Current 2.0 collaboration modes are documented for Python and Go; task mode is temporarily disabled in graph workflows and task-mode agents must be leaves. Template workflows are superseded by graphs in Python/Go, so cross-language feature parity must be checked. |

## Where Frontier Swarm fits

Frontier Swarm is a concrete eve reference topology—Planner → parallel specialists → parallel reviewers → Synthesizer—not a replacement for every runtime above. Its distinguishing design choices are inspectable typed handoffs, two explicit review stages, bounded fan-out, and repository-local eval definitions. Those are implementation facts, not evidence of superior results.

A fair comparison must pin models, prompts, tool access, budgets, retries, datasets, and failure handling, then report quality, latency, cost, and variance over repeated runs. See the [evaluation policy](evaluation.md) for the required disclosure.
